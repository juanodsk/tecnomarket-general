## Procedimiento uniforme de autorización

Para una operación empresarial, crear un rol QA_ALLOW con los permisos BUSINESS mínimos de esa operación y QA_DENY sin ellos. Añadir las sedes correctas a ambos actores. Mantener un control positivo y un negativo con datos idénticos y cambiar exclusivamente el token. Para hasAnyAuthority, quitar todos los permisos alternativos del rol negativo.

El caso `SHARED_SCOPE` viene concretado para cotizaciones: mismo usuario tiene QUOTATION_VIEW en A y ningún permiso empresarial en B, pero está asignado a B1. Los casos `SHARED_PERMISSION_SCOPE`, `INACTIVE_MEMBERSHIP` e `INACTIVE_ROLE` amplían la comprobación a 63 operaciones operativas con permisos declarados. Cada fila exige preparar los permisos exactos del endpoint, hacer login nuevo y configurar todos los recursos del negocio B. No reutilizar sin cambios el fixture inicial de QUOTATION_VIEW para una operación que necesita otro permiso. Probar tanto lecturas como mutaciones.

En recursos por sede ejecutar la misma ficha con un token que sí posee permiso empresarial y datos de otra sede; no quitar el permiso a la vez. Para listas sin branchId, exigir que solo devuelvan recursos de sedes autorizadas; no exigir 403 a una lista filtrada correctamente que devuelve 200.

Después de desactivar usuario/membresía/rol, el token antiguo puede quedar inválido (401). Para aislar el guard de membresía, iniciar nueva sesión de una cuenta todavía activa y repetir sobre el recurso: ahora debe ser 403. Con una cuenta global inactiva ni siquiera debe concederse login. Guardar ambos casos por separado.

## Filtros y páginas

Los casos FILTER individuales y por pares requieren datos positivos y negativos: crear tres filas, una que cumpla ambos filtros, otra solo el primero y otra solo el segundo. Comprobar IDs esperados, no solo número de resultados. Para clientes/órdenes usar valores del runId para evitar interferencia de otros datos de desarrollo.

Paginación: page=0/size=1, página siguiente, última, página vacía, page=-1, size=0, size=101. Los tres últimos deben dar 400 donde están declarados esos límites. Recorrer páginas y verificar ausencia de duplicados y metadatos consistentes. Probar sortBy permitido y sortDir; valores no admitidos no deben convertirse en SQL arbitrario. No aceptar un 200 con filas ajenas aunque el orden sea correcto.

Fechas invertidas en búsqueda de órdenes: receivedFrom > receivedTo debe dar 409. Para filtros sobre datos relacionados, comprobar que el ID del filtro no permita saltarse tenant/sede.
